# 模型优化记录

记录从"只会做 4 位补零加法"到"具备一定泛化能力"的迭代过程。

## 起点：基线模型的问题

当前模型在 `src/checkpoints/addition_transformer_v2.pt`，训练数据全是
`NNNN+NNNN=NNNN` 这种 4 位补零、左右等宽、答案 ≤ 4 位的格式。

`evaluate.py` 的变长泛化测试显示：训练分布外的样例几乎全错。

| 类型 | 样例 | 现状 |
| --- | --- | --- |
| 不补零短数 | `1+2=` | 错 |
| 位数不一致 | `1+999=` | 错 |
| 答案溢出 4 位 | `9999+9999=` | 错 |
| 输入超训练范围 | `12345+1=` | 错 |

根因：模型把"4 位补零"这个表层格式当成了任务定义的一部分。

## 优化方向

### 方向 1：数据层优化（最快见效）

不改模型，只改数据生成：

- 去掉零填充，让 `12+5=17` 这种自然变长样本进入训练集
- 训练数据按位数混合（1 ~ 4 位），并尽量均匀
- `MAX_NUMBER` 适度放宽，让答案能溢出到 5 位

预期：能解决"不补零"和"位数不一致"两类失败，对"答案溢出"也会有改善。

### 方向 2：模型层优化（需改架构）

替换 `PositionalEncoding`：

- 现在的正弦绝对位置编码绑定了 `max_len=32`，外推能力差
- 换成 RoPE 或 ALiBi，依赖相对位置，对长度泛化友好

预期：训练 4 位、推理 6 位这类外推任务才有可能成功。

### 方向 3：任务层优化（更激进）

让模型不直接输出答案，而是按位列竖式：

```
0123+0089=
  3+9=12 写 2 进 1
  2+8+1=11 写 1 进 1
  1+0+1=2 写 2
  0+0=0 写 0
=> 0212
```

把加法的"算法过程"显式写进训练目标，模型不需要"凭直觉"算大数加法。
这是 chain-of-thought 思路在小模型上的应用。

预期：理论上可以无限位数泛化，但训练数据生成和解码逻辑要重写。

## 迭代日志

### 2026-05-06：方向 1 启动

**改动文件**：`src/data.py`、`src/evaluate.py`、`src/train.py`

**数据生成策略**（`data.py`）：

- 去掉零填充：`make_addition` 改为 `f"{a}+{b}={a+b}"`
- 按 `(a 位数, b 位数)` 共 16 个桶均匀采样，每桶目标 `total // 16`
- 每桶受容量上限：`(1,1)` 桶最多 100 条，`(1,2)/(2,1)` 各最多 900 条，其余按目标值
- 因此 `total=50000` 实际生成约 42500 条，`ensure_data` 改为只判断文件是否存在
- 不再约束 `a + b < 10000`，答案自然出现 5 位

**实测分布**（`total=50000`）：

| 维度 | 数量 |
| --- | --- |
| 总行数 | 42525 |
| 1 位答案 | 55 |
| 2 位答案 | 3008 |
| 3 位答案 | 15243 |
| 4 位答案 | 21870 |
| 5 位答案 | 2349 |

5 位答案占 5.5%，足够提供"答案溢出"信号。

**评估侧同步**（`evaluate.py`）：

- `random_case()` 改用相同的位数均匀采样，保证同分布测试公平
- `predict` / `predict_batch` 默认 `max_len` 从 5 → 7，留给 5 位答案 + EOS 余量
- 默认数据/模型路径切到 `data/additions_v3.txt`、`checkpoints/addition_transformer_v3.pt`

**模型/超参未动**：架构、PE、层数、`d_model`、lr、epochs 全部保持 v2 设置。

**下一步**：训练 v3，对比同分布准确率与变长泛化测试结果，记录到本文件。
